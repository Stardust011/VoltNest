## 4. 已验证帧结构（置信度：高）

150 秒内 `0xFFB2` 共收到 32 帧，**全部 32 帧符合下述结构**，无一例外：

```
偏移  宽度  含义
[0]    1   报告 ID = 0x06（常量）
[1]    1   cmd（命令字）
[2]    1   payload 字节数 len
[3:5]  2   seq（小端 16 位；本次采集全为 0x0000）
[5:5+len]  payload
[5+len:64] 填充 0x00
```

校验方式：`5 + len <= 64` 且填充区必须全零。32/32 通过。

## 6.1 驱动关闭对照实验（已执行，决定性）

条件：`AJAZZ Driver（W1）` 完全退出（确认 PID 20684 结束，无任何 AJAZZ 进程），
监听 90 秒（14:42:04 – 14:43:34），日志 `tools/probe/capture_nodriver_1442.log`。

结果：**仍收到 4 帧，全部为 `06 fa 03 00 00 | 03 5a 00`**。

| 时间 | 帧 |
| --- | --- |
| 14:42:32.816 | `06 fa 03 00 00 03 5a 00` |
| 14:42:36.419 | `06 fa 03 00 00 03 5a 00` |
| 14:42:57.233 | `06 fa 03 00 00 03 5a 00` |
| 14:43:00.833 | `06 fa 03 00 00 03 5a 00` |

**结论（置信度：高）**：

1. `0xFA` 状态帧是**设备/接收器自主推送**，不依赖官方驱动，也不依赖任何主机请求。
2. 因此"2.4G 设备必须由宿主轮询"的假设**被推翻**。
3. 官方驱动关闭时设备仍可正常枚举与读取，**不存在独占或驱动替换需求**。

推送节奏特征：两帧一组、组内间隔约 3.6 秒，组间间隔约 21–30 秒
（两次采集均复现：`14:42:32.8 → 14:42:36.4` 与 `14:42:57.2 → 14:43:00.8`）。

## 6.2 电量字节（假设，置信度：中高）

`0xFA` 通道中出现频率最高的是 `03 5a 00`，在无任何驱动交互的情况下以约 30 秒周期重复出现：

```
cmd=0xFA  payload = [0x03, 0x5A, 0x00]
                      │     │     └─ 第 3 字节：0/1 之间跳变（14:38:36 曾变为 0x01）
                      │     └─ 0x5A = 90（十进制）
                      └─ 子标签 0x03
```

假设：**子标签 `0x03` = 电量百分比（0–100 直接值），第 3 字节 = 充电标志**。

支持证据：
- 数值 90 落在合理电量区间，且长时间稳定不漂移（符合"电量"而非"计数器"特征）。
- 该语义与公开的 249A 一代逆向结论一致（同为"百分比 + 充电标志"两字节），
  说明协议**语义层跨代保持，仅帧封装不同**。

反对/未排除的可能：
- `0x5A` 也可能是某个固定状态码（如"已连接/工作模式"），因为采集期间电量未发生变化，
  **没有观察到数值随电量变化的证据**。

**因此本条尚不能标记为"已验证"，必须通过后续实验确认。**

## 6.3 已评估但不适用于本机的方案（`0xF7` + Feature Report `0x05`）

外部资料（`Aiacos/ajazz-control-center` 一类项目）记录了一条 AJ 系列鼠标电量读取流程：
先 `SET_FEATURE` 发 `00 F7 00 ...` 建链，等待 30ms，再 `GET_FEATURE` 读 Report ID `0x05`，
电量在 `resp[3]`（Windows）或 `resp[2]`（Linux hidraw）。

该流程**不适用于本机设备**，依据是本机实测能力而非推断：

| 该方案的前提 | 本机实测 |
| --- | --- |
| 设备提供 Feature Report 通道 | **全部 7 个集合 `FeatureReportByteLength = 0`** |
| 存在 Report ID `0x05` | 仅观察到 Report ID `0x06` |
| 控制集合 Usage Page `0xFFFF` / `0xFF13` | 本机为 `0xFFB1` / `0xFFB2` / `0xFFB3` |
| VID:PID `0x3151:0x5007` 或 `0x0C45:0x8009` | 本机为 `0x7768:0x6426` |

`FeatureReportByteLength = 0` 意味着该设备根本不存在 Feature Report 通道，
`HidD_SetFeature` / `HidD_GetFeature` 在本机上必然失败。因此这套流程属于
**其他代际/其他型号的协议**，不可套用（符合计划书「不得猜测协议」的约束）。

本机可行的读取路径仍是 6.1 已验证的 `0xFA` 中断推送，且**无需任何建链握手**——
这一点比上述方案更简单。

### 可借鉴的唯一一点（与协议无关）

上述资料强调：「返回全零应视为"链路未建立"，不得显示为 0%」。
这一条与设备型号无关，属于状态机的正确性要求，应写入 Phase 2：
**解析失败 / 全零帧 / 越界值一律映射为 `Unavailable`，绝不回落到 `0%`。**

## 6.4 蓝牙模式（BLE）验证 —— Phase 4 硬件确认

设备支持双模。切到蓝牙模式并在 Windows 配对后实测：

- 枚举形态：`BTHLE\DEV_010000230435`，名称 `AJ159 NL`，**不是 BTHENUM（非经典蓝牙）**
- 系统级服务节点：`BTHLEDEVICE\{0000180F-...}`（蓝牙 LE 通用属性服务）、
  `{00001812-...}`（HOGP）、`{0000180A-...}`（设备信息）、`{00001800}`、`{00001801}`

GATT 枚举结果（5 个服务）：

| 服务 | 特征 | 属性位 | 说明 |
| --- | --- | --- | --- |
| `0x1800` Generic Access | `0x2A00` / `0x2A01` / `0x2A04` / `0x2AA6` | — | 常规 |
| `0x1801` GATT | `0x2A05` | 0x22 | Service Changed |
| **`0x180F` Battery** | **`0x2A19`** | **0x12 (READ+NOTIFY)** | ★ 标准电量 |
| `0x180F` Battery | `0x2BED` | 0x12 | Battery Level Status（含充电/临界位） |
| `0x180A` Device Info | `0x2A50` | 0x02 | PnP ID |
| `0x1812` HID over GATT | — | — | HOGP |

**读取结果：`0x2A19 = 90`。**

### 交叉验证结论（原计划 7.2 项，已解决）

| 路径 | 读数 |
| --- | --- |
| 2.4G 推送帧 `06 FA 03 00 00 03 5A 00` | 90（`0x5A`） |
| BLE 标准 Battery Service `0x2A19` | 90 |

两条**完全独立的物理路径**给出同一个值。这比"与官方驱动 UI 比对"更强：
排除了「`0x5A` 是某个固定状态码」的可能，`payload[1]` 就是电量百分比，**置信度升为高**。

附带发现：`0x2BED`（Battery Level Status）可用于获取充电状态，
比 2.4G 帧里那个来历不明的第 3 字节更可靠。

## 6.5 关键反例：接收器在场但设备已沉默

将鼠标切到蓝牙模式后，2.4G 接收器**仍然完整枚举**：

```
USB\VID_7768&PID_6426\20240401          Status=OK
HID\VID_7768&PID_6426&MI_00&COL01..04   Status=OK（鼠标/键盘/消费类/系统）
HID\VID_7768&PID_6426&MI_01&COL01..03   Status=OK（三个厂商集合）
```

但在 25 秒监听中，`0xFFB2` **收到 0 帧**（日志 `tools/probe/capture_btmode_1602.log`）。

**这条反例推翻了一个隐含假设**：PnP 枚举存在性**完全不能**用来判断设备是否可用。

更重要的推论——对推送型设备，「连续 N 次读取失败」这个判据**不成立**，
因为宿主根本没有发起读取，不存在"失败"。唯一可靠的信号是**静默时长**。
因此状态退化必须以「距上次有效推送的时间」为准，而不是失败计数。

## 7. 未决问题（阻塞 Phase 3 实现）

2. ~~**电量数值未交叉验证**~~ → **已解决（见 6.4）**：BLE 路径独立验证同为 90。
3. **命令下发格式未知**：`0xFFB1`（13 字节只写）的报文结构尚未采集，无法自行发起查询。
   影响：应用启动后无法立即取到电量，最长需等待一个推送周期（约 30 秒）。
   *注：BLE 路径可直接 `READ 0x2A19`，不存在此限制。*

## 8. 对开发计划的影响

1. **"2.4G 轮询"模型被推翻**：电量是设备约 30 秒一次的自主推送，
   Phase 2 对 2.4G 设备应改为**事件驱动 + 低频保底**，而非固定 2000ms Tick。
   这同时规避了"鼠标睡眠不应答"的已知陷阱。
2. **计划书需更正设备归类**：本机设备是 **NearLink（星闪）一代**，
   与公开逆向资料中的 `249A:5C2F`（XCTECH）为两代不同接收器，报文形态不同，
   **不可直接照搬字节布局**，但语义可借鉴。
3. **设备匹配规则必须是表驱动**：驱动 `config.xml` 已给出 8 个型号 × 2 种模式的
   VID/PID 对照，插件不应硬编码单一 `0x6426`。
4. **驱动共存风险已排除**：厂商通道可共享打开，驱动关闭后也照常工作，
   不需要替换驱动或 WinUSB。
5. **新增产品级约束**：仅靠被动推送时，应用启动后最长约 30 秒内无法显示电量。
   若要求"启动即显示"，必须补做 `0xFFB1` 命令通道的逆向。
